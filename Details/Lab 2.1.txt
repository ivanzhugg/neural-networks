ШАГ 4. Три визуализации

Требование: каждый график должен отвечать на конкретный вопрос.

Действие: для Sex и Pclass рассчитано среднее Survived по группам и построены столбчатые диаграммы. Для Age построены две гистограммы с одинаковыми границами интервалов. Каждый график создаётся через отдельный plt.figure, имеет заголовок и подписи осей.

Наблюдения: женщины выживали чаще мужчин; первый класс имеет большую долю выживших, чем третий. Возрастные распределения заметно перекрываются. Гистограмма показывает абсолютное количество пассажиров, поэтому сама по себе не даёт вероятность выживания для возраста.

Графики построены по всей таблице, как предусмотрено учебным шаблоном. Обязательный набор признаков остаётся фиксированным. Ни одна из этих сводок не используется для обучения imputer или scaler. Наблюдаемая связь не доказывает причинность: возможны связанные факторы и различия состава групп.

ШАГ 5. Воспроизводимый split

Требование: train/validation/test 70/15/15 с seed и стратификацией на обоих этапах.

Действие: создан массив позиций all_idx = np.arange(len(df)). Из него отделён test через test_size=0.15. Оставшаяся часть разделена с test_size=0.15/0.85. На втором этапе stratify получает y.iloc[train_val_idx], то есть метки именно оставшихся строк.

Получено:
train: 623 строки.
validation: 134 строки.
test: 134 строки.

Обоснование: число строк целое, поэтому доли получаются приблизительными. Нельзя просто дважды отделить по 15% от текущей таблицы: второй раз это были бы 15% от 85%, то есть 12.75% всей таблицы. Деление 0.15/0.85 исправляет этот масштаб.

stratify сохраняет близкое соотношение классов в каждой части. Это снижает риск получить случайно несопоставимые выборки. random_state фиксирует конкретные строки для повторного эксперимента.

X и y выбираются через iloc с одними и теми же индексами. Так признаки не расходятся со своими ответами. Проверены отсутствие пересечений, общая численность и полное покрытие всех исходных позиций. Повторное построение split дало те же индексы.

ШАГ 6. Демонстрация data leakage

Требование: объяснить, почему статистики нужно считать только по train.

Действие: отдельно рассчитаны full_age_median=28.0 и train_age_median=29.0. Первое значение используется только для демонстрации и не подставляется в рабочий preprocessing.

Обоснование: data leakage означает использование информации, которая не должна быть доступна при обучении. Если заполнять train медианой всех данных, значения validation/test повлияют на вход модели ещё до оценки. Даже без target это нарушает выбранный протокол эксперимента.

Малая разница медиан не оправдывает метод. Правильность определяется источником статистики, а не тем, насколько сильно изменился конкретный результат.

ШАГ 7. Построение make_preprocessor

Требование: разные типы признаков должны преобразовываться по разным правилам.

Действие: числовая ветка Pipeline содержит median imputer и StandardScaler. Категориальная ветка содержит most_frequent imputer и OneHotEncoder. ColumnTransformer применяет ветки к соответствующим спискам столбцов и объединяет результаты.

Теория числовой ветки:
Медиана берётся по наблюдаемым значениям train и заполняет пропуски. Она менее чувствительна к отдельным большим значениям, чем среднее. Затем StandardScaler преобразует каждый признак примерно как (x - mean_train) / std_train. Разные масштабы Age и Fare перестают определять вклад только за счёт единиц измерения.

Теория категориальной ветки:
Пропуск заменяется самой частой категорией train. One-hot создаёт отдельный индикатор для каждого известного значения. Это не навязывает числовое расстояние между классами обслуживания или портами посадки.

handle_unknown="ignore" означает, что новая категория при transform не вызывает ошибку и получает нули в индикаторах соответствующего исходного признака. sparse_output=False задаёт обычный плотный массив, удобный для дальнейшего сохранения.

Функция возвращает новый объект при каждом вызове. Это позволяет отдельно показать preprocessing и затем собрать полный pipeline без случайного совместного использования уже обученного экземпляра.

ШАГ 8. Fit на train и transform остальных частей

Требование: статистики preprocessing должны обучаться только на train.

Действие:
X_train_prepared = preprocessor.fit_transform(X_train)
X_val_prepared = preprocessor.transform(X_val)
X_test_prepared = preprocessor.transform(X_test)

Обоснование: fit определяет медианы, средние, дисперсии и категории. transform использует уже зафиксированные параметры. Отдельный fit на validation/test изменил бы систему представления и использовал бы информацию отложенных данных.

Получены 12 выходных признаков:
num__Age, num__SibSp, num__Parch, num__Fare;
cat__Pclass_1, cat__Pclass_2, cat__Pclass_3;
cat__Sex_female, cat__Sex_male;
cat__Embarked_C, cat__Embarked_Q, cat__Embarked_S.

Четыре числовых столбца сохранились, а три категориальных развернулись в восемь one-hot. Префиксы обозначают ветку ColumnTransformer.

Transform test на этом этапе не оценивает качество и не меняет параметры. Test-метрики появляются только после фиксации модели. Проверены одинаковое число выходных столбцов, соответствие числа строк и отсутствие NaN/inf.

ШАГ 9. DummyClassifier

Требование: сравнить модель с тривиальным решением.

Действие: DummyClassifier(strategy="most_frequent") обучен на train и предсказывает наиболее частый класс 0. На validation рассчитаны accuracy и F1.

Результат: accuracy=0.611940, F1=0.

Обоснование: даже предсказание только большинства даёт около 61% правильных ответов. Поэтому одна accuracy без baseline может выглядеть лучше, чем есть на самом деле. F1 равен нулю, потому что модель не находит ни одного положительного объекта.

ШАГ 10. Logistic Regression в полном Pipeline

Требование: объединить преобразования и классификатор, обучить на raw X_train.

Действие: создан Pipeline с именами шагов preprocessor и model. Последний шаг содержит LogisticRegression(max_iter=1000, random_state=SEED). Вызван logreg_pipeline.fit(X_train, y_train).

Обоснование: логистическая регрессия вычисляет взвешенную сумму подготовленных признаков и переводит её в вероятность положительного класса. Обучение подбирает веса, уменьшая ошибку классификации с учётом регуляризации. max_iter задаёт предел итераций оптимизации, а не число объектов.

Pipeline сначала обучает preprocessing на переданном train, затем модель. При predict он повторяет те же преобразования. Это снижает риск забыть imputation, scaling или получить другой порядок категориальных столбцов при оценке.

Pipeline сам по себе не гарантирует честность: вызов fit на всей таблице всё равно вызвал бы leakage. Здесь все fit и fit_transform получают только train.

ШАГ 11. Validation-метрики и confusion matrix

Требование: сравнить модели и понять типы ошибок.

Результат Logistic Regression на validation:
Accuracy: 0.835821.
F1: 0.792453.
Confusion matrix:
                 prediction 0   prediction 1
true 0                 70             12
true 1                 10             42

TN=70: правильно предсказан класс 0.
FP=12: предсказано выживание, но правильный класс 0.
FN=10: предсказан класс 0, но пассажир выжил.
TP=42: правильно предсказано выживание.

Accuracy=(TP+TN)/N. Precision=TP/(TP+FP). Recall=TP/(TP+FN). F1=2TP/(2TP+FP+FN). F1 показывает совместное качество precision и recall положительного класса.

Logistic Regression лучше Dummy и по accuracy, и по F1. На этом этапе используется validation, потому что именно он предназначен для анализа решений. Test пока остаётся финальной проверкой.

ШАГ 12. Пороги и ROC-AUC

Требование: показать, как один набор вероятностей даёт разные решения.

Действие: predict_proba(X_val)[:, 1] выбирает вероятность класса 1. Для каждого порога класс 1 назначается при p >= threshold. Рассчитаны precision и recall:

Порог    Precision    Recall
0.3      0.657143     0.884615
0.5      0.777778     0.807692
0.7      0.878049     0.692308

Обоснование: низкий порог объявляет положительными больше объектов. Recall растёт, но появляются дополнительные FP. В данном запуске при повышении порога precision растёт, recall падает. Рост precision не является универсальной гарантией для любого набора данных.

При особенно дорогих FN среди этих трёх вариантов разумен 0.3, поскольку он пропускает меньше положительных объектов. Это условное объяснение компромисса. Для финальной оценки в работе оставлен стандартный порог 0.5; порог не выбирался по test.

ROC-кривая показывает TPR против FPR при разных порогах. TPR совпадает с recall, FPR=FP/(FP+TN). ROC-AUC=0.892237 оценивает качество ранжирования. Он вычисляется по вероятностям, а не по одному набору бинарных ответов.

Дополнительная проверка AUC выполнена через попарное сравнение оценок положительных и отрицательных объектов. AUC равен доле корректно упорядоченных пар с половинным весом равенств. Независимый расчёт совпал со sklearn.

ЧАСТЬ 3. ОСНОВНЫЕ ВОПРОСЫ ДЛЯ ЗАЩИТЫ

Чем fit отличается от transform? Fit определяет параметры по данным, transform применяет готовые параметры.
Зачем stratify? Для близкого баланса классов в частях выборки.
Почему нельзя считать медиану по всей таблице? Это использует информацию отложенных данных.
Почему после preprocessing 12 признаков? Четыре числовых плюс восемь one-hot.
Зачем Dummy? Он показывает качество без использования связей между признаками и target.
Почему accuracy недостаточно? При дисбалансе большинство может дать высокую accuracy без распознавания меньшего класса.
Что произойдёт при снижении порога? Обычно растёт recall и увеличивается число положительных предсказаний.
Почему нельзя выбирать порог по test? Test перестанет быть независимой финальной оценкой.
Что именно переходит в ЛР3? Подготовленные массивы, метки, имена признаков и фиксированное разбиение пассажиров.

Для запуска следует открыть student.ipynb из Result, выбрать окружение .venv, перезапустить ядро и выполнить все ячейки. Личные пункты о готовности к защите требуют самостоятельной проверки.
